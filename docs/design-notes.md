# 设计笔记：为什么是这个形状

这份文档记几条设计取舍的来龙去脉，给以后改这块代码的人看。没有实现细节，只有判断依据。

## 一、为什么不写死 RVA

RVA 是最省事的定位方式：反汇编器里看到 `0x1842A0` 有一条 call，脚本里就写 `0x1842A0`。

省事，也最容易错得无声无息。

目标程序一升级，前面插进几行代码，后面所有函数地址整体后移。脚本照常跑，照常报「成功」——因为它验的是同一个错地址。**它验证的不是补丁对不对，是那个数字有没有变。** 这两件事看起来一样，出事的时候差别很大。

签名定位换了个前提：不假设位置不变，每次动手都重新找。找得到，说明这个位置上还有那段上下文；找不到，说明目标变了，该停下来看。代价是每次多扫一遍文件，几 MB 的 DLL 也就几十毫秒，不值一提。

## 二、为什么失败要整体拒绝

有个常见的写法：找到几条改几条，找不到的打个警告继续。

这个做法的隐含假设是「补丁之间互不相干」。实际不是。一组补丁往往共享同一个前提——比如都基于某个函数的开头长这样。这个前提不成立了，可能只有一条签名失效，但其余几条仍然能匹配上，只是匹配到的已经是别的东西。**部分成功比整体失败更难查。**

所以这里反过来：任何一条不过，整批放弃，一个字节都不写。

同一条理由也解释了为什么返回的字节序列是新对象而不是原地修改。调用方拿到的要么是完整的补丁后结果，要么是异常，没有中间态。

## 三、签名怎么选

三条经验，按重要性排。

**签名要取补丁点之前的一段。** 这是最容易踩的坑。把要改的那几个字节也写进签名，看起来天经地义，实际上打完补丁签名就没了：`verify` 找不到，`apply` 也没法判断是不是已经打过了，每次跑都当第一次处理。

代码里把这条做成了构造时的硬性检查，`at` 小于签名长度直接抛异常。

**长度够用就行，不是越长越好。** 太短会撞上多处；太长的代价是你把一堆无关字节绑进了匹配条件，目标程序改动任何一处无关代码，你的签名就失效了。经验值是一两个指令加几个参数寄存器，具体得看那块代码有多独特。

**匹配条件不带通配。** 通配符会让「唯一」这个判定变得模糊——撞上几个候选都算命中，工具就没法替你决定了。宁可让签名长一点，也不要引入通配。

## 四、幂等与 verify

`apply` 和 `verify` 用的是同一套定位逻辑，区别只在最后一步：`apply` 写盘，`verify` 只报告。

两者要能重复跑，前提是**签名在补丁前后都存在**。这就是第三节第一条的作用。达成了这个前提，`apply` 可以靠「当前位置已经是替换后的字节」来判断跳过，`verify` 可以靠「当前位置是替换后的字节」来报告通过。都不需要额外记录状态。

顺带说一句，`expect` 的语义是「这里应该还是旧字节」，不是「这里必须是旧字节」。前者是核对，后者会让第二次 `apply` 必然失败。代码里把这两件事拆开了：`resolve_offset()` 只负责定位，`apply_patches()` 才看 `expect`，而且先判断是不是已经打过了。

## 五、改调用点，还是改被调用的东西

遇到目标函数行为不对，有两条路：改调用方，或者改被调用方本身。

**优先改调用点。** 被调用的函数往往不止一个调用者，改它等于替所有人做决定，其中有些人你根本不知道存在。调用点的语义边界清楚——你只影响这一处。

还有一层：如果目标函数属于某个运行时、加载器或框架，它自己也在读同样的状态，那动它的风险是「可能让整个程序起不来」，而改调用点的风险只是「这一处补丁失效」。风险不对等。

## 六、已知边界

**只支持等长替换。** 加长或缩短会挪动后面所有偏移、破坏节区表，那属于另一类工具（重写 PE）。这里不做。

**签名撞车时不做自动消歧。** 出现多次就停，由人去补足上下文。自动加长签名听起来聪明，实际上是在用机器猜测替代人的判断，而这一步恰恰最需要人确认。

**不认通配、不认正则、不认跨节区匹配。** 每加一种匹配方式，「唯一」的判定就多一层解释空间。这个工具的定位是保守，不是万能。

**不负责判断补丁内容对不对。** 它只保证：你写的替换字节，会落在你指的那一处，落之前核对过、落之后可复核。至于这几个字节改了之后行为对不对，那是人的事。
